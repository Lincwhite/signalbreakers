## 1. CORE GAMEPLAY LOOP ARCHITECTURE

### Loop Sequence (Detailed)

```
[MISSION START]
    ↓
Receive Transmission → Decode Signal Pattern → Program Robot → Execute Code
    ↑                                                      ↓
Collect Lore ← Verify Result ← Visual/Audio Feedback ← [RESULT]
    ↓
Advance Story → Unlock Next Mission → Update Progression Data
    ↓
[MISSION COMPLETE / RETRY]
```

### Loop Timing Targets

| Phase | Duration | Notes |
|-------|----------|-------|
| Receive transmission | 2–5 seconds | Animated signal arrival; brief story text |
| Decode signal pattern | 10–60 seconds | Depends on puzzle complexity; Explorer mode shows hints |
| Program robot | 30–180 seconds | Core gameplay phase; player writes/edits code |
| Execute code | 5–15 seconds | Robot animation plays through solution |
| Verify result | 2–5 seconds | Success/failure feedback with visual/audio cues |
| Collect lore (if applicable) | 3–8 seconds | Animation + text display; skippable |
| Advance story | 5–15 seconds | Story beat triggers next mission unlock |

**Total average mission time:** 5–10 minutes (varies by difficulty mode and player skill)

### State Machine Overview

The game operates as a finite state machine with the following states:

```
MENU → LOADING → MISSION_SELECT → PUZZLE_SETUP → PROGRAMMING → EXECUTION → RESULT → LORE_COLLECTION → STORY_BEAT → MISSION_COMPLETE → MENU
                                                              ↓
                                                          RETRY (back to PROGRAMMING)
                                                              ↓
                                                        QUIT_TO_MENU
```

**State transitions:**
- MENU → LOADING: Player selects mission from district map
- LOADING → MISSION_SELECT: Load completes; show district overview
- MISSION_SELECT → PUZZLE_SETUP: Player confirms mission; load puzzle data
- PUZZLE_SETUP → PROGRAMMING: Show code editor with available instructions
- PROGRAMMING → EXECUTION: Player presses "Run"; validate code syntax first
- EXECUTION → RESULT: Robot completes (or fails); show outcome
- RESULT → LORE_COLLECTION: If lore fragment earned, play animation; otherwise skip
- LORE_COLLECTION → STORY_BEAT: Play story text/dialogue; advance narrative
- STORY_BEAT → MISSION_COMPLETE: Update save data; unlock next mission if applicable
- MISSION_COMPLETE → MENU: Return to district map

## 2. SIGNAL PROCESSING SYSTEM

### Signal Data Structure

Each signal is represented as a structured object with the following properties:

| Property | Type | Description | Example |
|----------|------|-------------|---------|
| `id` | String | Unique identifier | "SIG_D1M03_001" |
| `type` | Enum | Signal category | ACTIVE, INTERFERENCE, ENCODED, BLOCKED, LORE |
| `color_hex` | String | Visual color representation | "#00F5FF" (cyan) |
| `pattern` | Array | Sequence of visual elements | ["solid", "pulse", "solid"] |
| `duration_ms` | Integer | How long signal persists | 3000 |
| `data_payload` | String | Decoded content (if applicable) | "REMEMBER" |
| `source_district` | Integer | District origin (1–8) | 1 |
| `is_dream_signal` | Boolean | Whether generated by AETHEL | false |

### Signal Parsing Pipeline

```
Raw Input → Pattern Recognition → Type Classification → Data Extraction → Codebook Lookup → Player Display
```

**Step-by-step:**

1. **Raw Input:** Signal arrives as visual pattern (color + shape + animation)
2. **Pattern Recognition:** System analyzes pattern structure (e.g., "repeating every 3 seconds")
3. **Type Classification:** Assigns signal type based on color/pattern rules defined in Codebook
4. **Data Extraction:** If encoded, extracts hidden data using decoding algorithm specific to signal type
5. **Codebook Lookup:** Cross-references with player's unlocked Codebook entries
6. **Player Display:** Shows decoded result in puzzle area with visual feedback

### Decoding Algorithms by Signal Type

| Signal Type | Decoding Method | Example |
|-------------|-----------------|---------|
| ACTIVE | Direct read — no transformation needed | Cyan pulse = "move forward" |
| INTERFERENCE | Remove noise, extract base pattern | Magenta zigzag → filter → reveals hidden cyan signal underneath |
| ENCODED | Rhythmic pattern decoding (Morse-like) | 3 short + 2 long = "R"; player must identify rhythm and map to Codebook |
| BLOCKED | Requires external signal to unblock | Grey static → player programs robot to send matching frequency |
| LORE | Spiral/wave pattern with gradient | Gold-cyan spiral → extracts text fragment from Deep Archive database |

### Dream Signal Generation (AETHEL)

Dream signals are procedurally generated using the following algorithm:

```python
def generate_dream_signal(citizen_emotion, time_of_day, district):
    base_color = emotion_to_color(citizen_emotion)  # joy=gold, anger=red, etc.
    complexity = random.uniform(0.3, 0.8)  # Higher = more complex pattern
    duration = random.randint(2000, 10000)  # 2–10 seconds
    
    pattern = []
    for i in range(int(complexity * 10)):
        pattern.append(random.choice(["pulse", "fade", "blink", "wave"]))
    
    return Signal(
        type="DREAM",
        color_hex=base_color,
        pattern=pattern,
        duration_ms=duration,
        is_dream_signal=True,
        source_district=district
    )
```

**Purpose:** Creates unique dream signals that feel organic and emotionally resonant. Each dream signal is different but follows consistent visual rules so players can learn to recognize them.

## 3. ROBOT PROGRAMMING ENGINE

### Instruction Set (Districts 1–2)

| Instruction | Syntax | Parameters | Effect |
|-------------|--------|------------|--------|
| Move | `Move` | None | Robot advances one tile forward in current facing direction |
| TurnLeft | `TurnLeft` | None | Robot rotates 90 degrees counter-clockwise |
| TurnRight | `TurnRight` | None | Robot rotates 90 degrees clockwise |
| DropPackage | `DropPackage` | None | Places one package at current tile (if carrying packages) |
| Load(n) | `Load(3)` | Integer n | Robot picks up n packages from warehouse (must be adjacent to warehouse) |
| Repeat(n, [instructions]) | `Repeat(5, [Move, Drop])` | Integer n + array of instructions | Repeats enclosed instruction sequence n times |
| IF signal == TYPE THEN ... ELSE ... | `IF cyan THEN Left ELSE Right` | Signal type + action | Branches based on current signal color at robot's location |

### Code Validation Pipeline

```
Player Input → Syntax Check → Semantic Check → Execution Simulation → Result Comparison
```

**Step-by-step:**

1. **Syntax Check:** Validates instruction format (e.g., `Repeat(5, [Move, Drop])` is valid; `Repeat 5 Move Drop` is invalid)
2. **Semantic Check:** Validates logic (e.g., `DropPackage` without packages is a warning but not error; `Load(10)` when warehouse has only 5 packages is an error)
3. **Execution Simulation:** Runs code in memory to check for infinite loops, out-of-bounds movement, or unreachable instructions
4. **Result Comparison:** Compares robot's final state (position, packages delivered, signals processed) against mission objective

### Execution Feedback by Difficulty Mode

| Mode | Real-time Feedback | Post-execution Feedback | Error Handling |
|------|-------------------|------------------------|----------------|
| Explorer | Robot highlights each step as it executes; shows current instruction in Codebook panel | Green checkmark for correct steps; red X for failures with hint text | Auto-rewinds to last successful step on failure |
| Engineer | Shows efficiency counter (instructions used vs. optimal); no step highlighting | Score based on instruction count; shows optimal solution if player exceeded by >50% | Rewinds to start; shows efficiency comparison |
| Blackout | No feedback during execution; robot moves silently | Submit-only: result shown after full execution; hidden score revealed only after completion | Rewinds to start; no hints until player requests "View Solution" |

### Code Editor UI Components

The code editor consists of the following interactive elements:

| Component | Function | Interaction |
|-----------|----------|-------------|
| **Instruction Palette** | Shows available instructions for current mission | Drag-and-drop or click-to-insert into code area |
| **Code Area** | Text field where player writes/edits program | Supports typing, paste, undo (Ctrl+Z), redo (Ctrl+Y) |
| **Run Button** | Executes the programmed code | Triggers execution pipeline; disabled during execution |
| **Reset Button** | Clears robot position and state without clearing code | One-click reset; code preserved |
| **Hint Button** | Shows contextual hint based on current mission | Explorer mode: shows what to do; Engineer mode: shows efficiency tip; Blackout mode: shows nothing until submission |
| **Codebook Toggle** | Opens/closes reference panel | Click or keyboard shortcut (C key) |

## 4. DIFFICULTY MODE BEHAVIOR MATRIX

### Mode Switching Rules

- Players can switch difficulty modes at any time from the pause menu
- Progress is tracked separately per mode (high scores, completion status)
- Switching modes does NOT reset current mission progress (code editor state preserved)
- Switching to Blackout mode mid-mission reveals hidden scoring; switching back hides it again

### Detailed Behavior Comparison

| Feature | Explorer | Engineer | Blackout |
|---------|----------|----------|----------|
| **Hint system** | 3 progressive hints per mission: (1) What to do, (2) How to do it, (3) Example solution | 2 hints: (1) What to optimize, (2) Efficiency target | 0 hints during play; "View Solution" available after submission |
| **Timer** | Optional; can be disabled in settings. If enabled, shows elapsed time but doesn't affect score | Recommended; timer affects efficiency score (faster = better within reason) | No visible timer; internal timer tracks execution speed for hidden scoring |
| **Visual feedback during execution** | Robot highlights current instruction; Codebook panel shows matching entry | Efficiency counter updates in real-time; optimal path shown as faint overlay after completion | Robot moves silently; no visual indicators until result screen |
| **Scoring algorithm** | Pass/fail based on whether objective is met. No numerical score. | Score = (optimal_instructions / actual_instructions) × 100, capped at 100%. Bonus for speed. | Hidden score = correctness (70%) + elegance (20%) + speed (10%). Revealed only after completion. |
| **Retry behavior** | Unlimited retries; no penalty | Unlimited retries; best score tracked and displayed | Unlimited retries; best hidden score tracked |
| **Achievement eligibility** | All achievements available | Some achievements require Engineer mode (e.g., "Efficiency Expert") | Some achievements require Blackout mode (e.g., "Blind Master") |

### Score Display by Mode

```
Explorer: [✓ Mission Complete] — No score shown
Engineer: [Score: 85/100] — Optimal: 6 instructions, You used: 7
Blackout: [Hidden Score: ???] — Revealed after completion: "Elegance: B | Speed: A- | Correctness: S"
```

## 5. SAVE/LOAD SYSTEM ARCHITECTURE

### Save Data Structure

Save data is stored as a JSON object with the following structure:

```json
{
  "player_id": "uuid-v4-string",
  "current_district": 1,
  "completed_missions": ["D1M01", "D1M02"],
  "lore_fragments_collected": ["LF01", "LF02"],
  "difficulty_preferences": {
    "default_mode": "Explorer",
    "per_district_modes": {"1": "Explorer", "2": "Engineer"}
  },
  "high_scores": {
    "D1M01": {"Explorer": null, "Engineer": 85, "Blackout": null},
    "D1M02": {"Explorer": null, "Engineer": 72, "Blackout": null}
  },
  "settings": {
    "text_scale": 1.0,
    "colorblind_mode": "none",
    "timers_enabled": true,
    "audio_volume": 0.8,
    "music_volume": 0.7
  },
  "playtime_seconds": 3600,
  "last_save_timestamp": "2026-11-23T01:30:00Z"
}
```

### Save Triggers

| Event | Auto-save? | Manual save slot | Notes |
|-------|------------|------------------|-------|
| Mission complete | Yes | No | Saves progress, high scores, lore fragments |
| Lore fragment collected | Yes | No | Updates lore_fragments_collected array |
| District unlocked | Yes | No | Updates current_district if advanced |
| Settings changed | No (dirty flag set) | Optional | Saves on next auto-save or manual save |
| Exit game | Yes | No | Full state serialization |
| Manual save | N/A | Up to 3 slots | Player chooses slot name and location |

### Cloud Sync (Windows/Steam)

- **Platform:** Steam Cloud API
- **Sync frequency:** On every auto-save event + on exit
- **Conflict resolution:** Latest timestamp wins; if timestamps match, manual save takes priority
- **Storage limit:** 1 MB per game (save data is ~2–5 KB, well within limits)

### Cloud Sync (Android/Google Play)

- **Platform:** Firebase Realtime Database (free tier)
- **Sync frequency:** On every auto-save event + on exit
- **Conflict resolution:** Last-write-wins with 10-second debounce to prevent race conditions
- **Offline support:** Saves locally if no connection; syncs when reconnected

### Save File Locations

| Platform | Local Path | Cloud Path |
|----------|------------|------------|
| Windows (Steam) | `%APPDATA%\Signalbreakers\save.json` | Steam Cloud (auto-synced) |
| Android | `/data/data/game.signalbreakers/files/save.json` | Firebase Realtime Database |

## 6. PROGRESSION & ACHIEVEMENT TRACKING

### Achievement System Architecture

Achievements are defined as data objects with the following properties:

```json
{
  "achievement_id": "first_signal",
  "title": "First Signal",
  "description": "Complete your first mission.",
  "condition": {"type": "mission_complete", "mission_id": "D1M01"},
  "rarity": "common",
  "points": 10,
  "unlocked": false,
  "unlock_timestamp": null
}
```

### Achievement Categories

| Category | Achievements | Unlock Condition |
|----------|-------------|------------------|
| **Story** | First Signal, Loop Master, Conditional Thinker, Signalbreaker | Complete specific missions/districts |
| **Difficulty** | Explorer's Path (complete D1–2 in Explorer), Engineer's Pride (complete D1–2 in Engineer), Blackout Legend (complete any mission in Blackout) | Complete missions in specific modes |
| **Collection** | Lore Hunter, Dream Weaver, Free City | Collect lore fragments; achieve specific endings |
| **Efficiency** | Code Minimalist (solve any mission using ≤50% of naive solution's instructions), Pattern Recognizer (complete 3 missions without hints) | Performance-based metrics |

### Progression Bar System

Each district has a visual progression bar that fills as missions are completed:

```
[████████░░░░] 67% Complete — District 1: Token Town
```

- **Visual feedback:** Bar fills with cyan glow; completed mission icons turn gold
- **Hover tooltip:** Shows which missions are complete, in-progress, and locked
- **Accessibility:** Text label always visible; bar is supplementary visual cue

## 7. AUDIO SYSTEM INTEGRATION

### Audio Event System

Audio events are triggered by game state changes:

| Game Event | Audio Cue | Volume | Notes |
|------------|-----------|--------|-------|
| Signal decoded (success) | Ascending cyan chime | 80% | Distinct pitch per signal type |
| Signal decoded (failure) | Descending magenta tone | 70% | Shorter than success cue |
| Robot moves | Gear whir + footstep | 50% | Fades based on distance from "camera" |
| Package dropped | Metallic clink | 60% | Varies by package weight (Load(n)) |
| Hint revealed | Soft bell ping | 40% | Only in Explorer mode |
| Mission complete | Full chord progression | 90% | District-specific melody |
| Lore fragment collected | Ethereal swell + gold chime | 85% | Unique per fragment ID |

### Audio Mixing Rules

- **Music volume:** Separate slider (default 70%); ducks by 20% during dialogue
- **SFX volume:** Separate slider (default 80%)
- **Voice volume:** Separate slider (default 90%)
- **Master volume:** Controls overall output (default 100%)
- **Mute all:** Keyboard shortcut (M key); persists across sessions

### District Music Transitions

Music transitions use crossfade over 2–3 seconds to avoid jarring cuts:

```
[District 1 Music] ──crossfade──→ [District 2 Music]
     80% volume              50%          80% volume
     ↓                         ↓            ↓
   0s → 1s → 2s → 3s → 4s → 5s → 6s
```

**Implementation:** Godot's `AudioStreamPlayer` with `mix_target` and `autoplay` properties for seamless transitions.

## 9. PERFORMANCE TARGETS

### Frame Rate Targets

| Platform | Target FPS | Minimum FPS | Notes |
|----------|------------|-------------|-------|
| Windows (Recommended) | 60 | 30 | Godot's default physics tick is 60Hz; target 60 FPS for smooth animation |
| Windows (Minimum hardware) | 30 | 24 | Acceptable for puzzle game; reduce visual effects if needed |
| Android (High-end) | 60 | 30 | Vulkan backend preferred; disable post-processing if needed |
| Android (Low-end, 2GB RAM) | 30 | 24 | Disable particle effects; use simpler shaders |

### Memory Budgets

| Platform | Total RAM | Game Budget | Notes |
|----------|-----------|-------------|-------|
| Windows | 8 GB+ recommended | < 500 MB | Godot editor overhead + game runtime |
| Android (4GB+) | 4 GB+ | < 200 MB APK + OBB | Compress textures; use Ogg for audio |
| Android (2GB minimum) | 2 GB | < 150 MB APK + OBB | Strip debug symbols; minimal asset quality |

### Load Time Targets

| Load Type | Target Duration | Notes |
|-----------|-----------------|-------|
| Initial game launch | < 5 seconds | Show loading screen with tip/lore fragment during load |
| Mission transition | < 2 seconds | Preload next district assets in background |
| Save/load from menu | < 1 second | JSON serialization is fast; avoid disk I/O bottlenecks |
